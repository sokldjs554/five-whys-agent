# 접수는 빨랐지만 조사 완료까지 19초가 걸린 이유

한꺼번에 새 조사 42건을 제출했을 때, 접수된 32건의 HTTP 202 응답 시간은 p95 **27.87ms**였다. 사용자가 결과를 받을 수 있을 때까지는 p95 **19.32초**가 걸렸다. 같은 32건의 큐 대기 시간은 p95 **18.70초**, 워커 실행 시간은 p95 **0.76초**였다. 이 부하에서 가장 먼저 확인할 지표는 대기 중인 작업 수와 가장 오래 기다린 작업의 대기 시간이다. [요청별 시간·작업별 대기 시간·자원 샘플](local-run.json)

## 두 종류의 요청에서 관찰한 결과

완료 보고서 읽기는 준비 단계에서 만든 실제 보고서 하나를 재사용했다. 새 조사마다 독립된 ID를 만들었고, 같은 한국어 질문으로 규칙 계획기와 실제 MCP stdio 도구 세 개를 호출했다. 접수한 모든 조사에서 인용이 있는 답을 확인했다. 모델 호출은 0회였다.

| 작업 | 부하 | 결과 |
| --- | --- | --- |
| 완료 보고서 GET | 동시 클라이언트 1 / 4 / 12명, 단계별 96회 | 288/288 HTTP 200. 응답 p95 각각 2.13 / 7.11 / 19.78ms |
| 새 조사 POST | 동시 클라이언트 12명, 총 42회, 약 83ms 동안 제출 | HTTP 202가 32건, HTTP 429가 10건. 429의 `Retry-After`는 모두 5초 |
| 작업 상태 GET | 버스트에서 접수한 32건의 완료를 순서대로 폴링 | 72/72 HTTP 200, 응답 p95 17.20ms |
| 결과 검증 | 접수 기록을 기준으로 각 작업의 결과 확인 | 32/32건 완료, 각 3개 도구 호출·3개 인용. 최초 제출부터 마지막 결과 HTTP 검증까지 20.53초 |
| 회복 확인 | 큐를 비운 뒤 새 조사 1건 | HTTP 202, 대기 2.59ms, 생성부터 완료까지 0.572초 |

버스트에서 큐와 실행 중 작업을 합친 표본 최댓값은 32건으로 코드의 동시 수용 한도와 일치했다. 모든 단계에서 기록한 HTTP 요청 444건 중 5xx와 네트워크 오류는 0건이었다. 429는 접수 거절로 따로 집계했고 자동 재시도는 하지 않았다. `p95`는 오름차순 `ceil(0.95 × 표본 수)` 번째 값이다. 각 분포의 백분위는 서로 더할 수 없다.

## 재현과 측정 조건

저장소 루트에서 앱 의존성이 설치된 Python을 사용한다. 실행 중인 서비스 주소를 입력할 필요가 없다.

```sh
python -m pip install -e .
python scripts/bench_desk.py --output /tmp/fivewhys-desk-load-1.json
```

측정기는 앱 소스를 임시 디렉터리에 복사한 뒤 새 SQLite DB와 Uvicorn 워커 1개를 시작한다. 서버는 랜덤 포트의 `127.0.0.1`에만 바인딩한다. Redis와 모델 서버를 연결하지 않고 HTTP 요청당 새 연결을 연다. 단계별 요청 횟수와 동시성을 고정하고 전체 측정을 5분으로 제한한다. 종료하면 서버와 임시 DB를 정리한다. [실행 스크립트](../../../scripts/bench_desk.py)

- **시간 기준** — HTTP 응답은 클라이언트의 단조 시계로 측정했다. 대기·실행·총시간은 상태 API에 기록된 `created_at`, `started_at`, `finished_at`의 차이다. 상태 폴링 간격은 0.5초다. 결과 전달이나 브라우저 렌더링 시간은 작업 총시간에 포함되지 않는다.
- **자원** — 측정 당시 공유 Linux 환경의 cgroup은 CPU 4코어 상당의 할당량과 메모리 16GiB 한도였다. API·자식 프로세스의 RSS 합을 0.25초 간격으로 읽은 최댓값은 162.1MiB였다. 공유 메모리 페이지가 중복 집계될 수 있다. 같은 호스트에서 클라이언트도 실행했다.
- **버전과 범위** — 측정한 `src/fivewhys` 복사본의 SHA-256은 `c8f654a59e851c314cbbd1f0cb678ab00542cccb0c5ed59bcf463dc7a44e8ed6`이다. 원자료에 Python과 패키지 버전도 저장했다. 읽기 단계는 각 1초 미만이었다. 이 수치는 단일 로컬 실행의 응답 분포이며 지속 가능한 운영 RPS, 실제 사용자 수, LLM 추론 용량은 별도 실험이 필요하다.

## 다음 실험 설계

1. **부하 목표와 실패 기준을 먼저 정한다.** 연습용 목표를 예로 들면, 새 조사 초당 0.5건에서 접수된 작업의 완료 p95 5초 이하, 보고서 조회 p95 100ms 이하, 5xx·데이터 유실 0건이다. 429 비율도 전체 제출을 분모로 기록한다. 이번 단일 실행에서 접수된 작업당 평균 실행 시간은 0.625초였다. 워커 한 개가 계속 바쁘다고 가정하면 약 1.6건/초가 계산상 상한이다. 반복 측정으로 그 근처에서 큐가 어떻게 변하는지 확인한다.
2. **k6에서 도착률을 고정한다.** 격리된 스테이징에서 완료 보고서 GET을 초당 10→30→60건, 새 조사 POST는 10초당 2→5→10건으로 각각 1분씩 보낸다. 단계마다 큐를 비운 뒤 같은 순서로 세 번 반복한다. `constant-arrival-rate`와 `dropped_iterations`를 사용하면 서버가 느려졌을 때 부하 생성기도 함께 느려지는 현상을 확인할 수 있다. 목표 부하와 현재 자원 예산에 맞춰 각 단계의 도착률을 조정한다.
3. **사용자 입장에서 하나의 값을 기록한다.** Locust로 접수→상태 조회→첫 유효 결과 표시까지를 한 작업으로 측정한다. 큐 길이, 최고 대기 시간, 429/5xx, 워커 실행 시간, 결과 GET p95, CPU·RSS를 같은 시간축에 둔다. 유입률이 안정된 구간에서만 리틀의 법칙 `L = λW`로 평균 대기·실행 작업 수를 점검한다. 순간 버스트의 p95를 이 식에 대입하면 잘못된 용량 추정이 된다.
4. **한 가지 변경만 비교한다.** 완료 조회가 병목이면 같은 부하에서 Redis 활성/비활성을, 조사 큐가 병목이면 작업 실행 프로세스 재사용 등을 비교한다. 현재 SQLite 단일 워커 설계를 확장할 때는 워커 중단·재시작, 중복 접수, 429 이후 재시도 및 데이터 복구도 다시 검증한다. 결과에는 처리량뿐 아니라 가장 느린 사용자 한 명의 재현 가능한 요청을 남긴다.
